# Чат Qwen и сохранённая выжимка

В объединённой ветке патчи из этой инструкции уже включены в код. Для запуска используйте [инструкцию финального релиза](final_release_operator.md). В приватном чате маршрут `/api/qwen/brief` принимает `dialog_id` и `position` и открывает тот же сохранённый отчёт только владельцу диалога. Общая выжимка по `run_id` читает общий журнал.

Применение согласует владелец общей ветки. Патчи проверены на исходном AI Core `f8b93b1` и на актуальной сборке `b71424d`. Коммиты Qwen содержат модули и отдельные патчи. Патчи предназначены для пробной копии и согласования с Тимуром и Андреем.

```sh
git apply --check llm_lab/patches/0001-chat-wiring.patch \
  llm_lab/patches/0002-qualitative-synthesis.patch llm_lab/patches/0003-core-evidence.patch
git apply llm_lab/patches/0001-chat-wiring.patch \
  llm_lab/patches/0002-qualitative-synthesis.patch llm_lab/patches/0003-core-evidence.patch
. llm_lab/configs/mac-m5.env
export PM_LLM_URL PM_LLM_MODEL PM_QWEN_CHAT_ENABLED PM_QWEN_QUALITATIVE
export PM_PRIVATE_DIR="$QWEN_PRIVATE_STATE"
cp llm_lab/prompts/synthesis-grounded.ru.txt "$PM_PRIVATE_DIR/synthesis-grounded.ru.txt"
export PM_LLM_PROMPT_FILE="$PM_PRIVATE_DIR/synthesis-grounded.ru.txt"
python app.py serve --port 8080
```

`QWEN_PRIVATE_STATE` должен указывать на созданную приватную папку вне Git. `PM_LLM_PROMPT_FILE` проверяет, что путь лежит вне рабочей копии. Синтетический запуск использует штатные данные AI Core. Для R-09 установите `PM_WORKBOOK` и `PM_CASE_CONFIG` из разрешённых файлов и импортируйте выбранные диапазоны интервью и конкурентного исследования через `app.py import`. Файлы, ответы, БД и настройки источников этого прогона находятся в закрытом локальном каталоге. Подключайте отдельный каталог состояния для прогона и тестового согласования задачи.

## Обзор изменений

| Патч | Изменение |
| --- | --- |
| `0001-chat-wiring.patch` | Включаемая HTTP-обвязка, подключение отдельного компонента и транзакционное согласование правок через `ai_store.decide`. |
| `0002-qualitative-synthesis.patch` | Включаемое сжатие контекста финального синтеза. Состав источников, факты Python, исходные ссылки и схемы проходят прежние проверки. Сопоставимость нормализованных цен передаётся в модель как серверное наблюдение. |
| `0003-core-evidence.patch` | Описание релиза из журнала, покрытие добавления в корзину, поиск согласованных задач, план и сохранённая оценка эффекта. |

Чат использует `investigation.analyze`, штатный Python-расчёт и ограниченный многошаговый выбор инструментов. Прогресс поступает от `live_runs`. При перезагрузке можно повторно открыть завершённые сообщения. Серверное прерывание текущего расследования в этой ревизии `live_runs` отсутствует. Сворачивание скрывает окно, пока задача продолжает выполняться. Временный ход прогона хранится в процессе.

`pm.chat.consult` принимает вопрос до 500 символов и настройки области. В естественном уточнении или режиме «Уточнение» используется предыдущий вопрос и при явной отсылке короткая формулировка предыдущей гипотезы. Источники собираются заново. Новая тема начинается без этих текстов. Область содержит только `config`, `memory`, `metrika`, `web` и `task_id`. Для исторического сравнения пользователь выбирает два окна и ряд во встроенной форме базы знаний. Выбор другого ряда меняет продукт в историческом запросе. Для истории релизов или предложений выберите ряд продукта и второе окно. Для похожих расследований и решений заполните поиск базы знаний и нажмите «Спросить об истории в чате». Исторический запрос ограничивает сбор источниками архива и проверяет явный продукт при чтении прежних решений. Когда выбранной записи или периода нет, чат показывает отсутствие данных. Текущий обзор и воронка используют продукт, заданный доверенной конфигурацией стенда. Если требуются сопоставимые окна или неизвестен идентификатор согласованной задачи для проверки эффекта, чат запрашивает уточнение.

`pm.brief.release_brief` читает отчёт по `run_id`. На странице обзора подтягивается последнее подходящее расследование из журнала. При первом запуске сформируйте отчёт через основной экран агента с запросом, который включает релиз. Первая выжимка появится после завершения расследования. Из сохранённого отчёта берутся числа, шаги, гипотезы, доступность источников и следующий шаг.

«Как измерить эффект?» раскрывает показатель, базовый период и контроль из того же отчёта. Уточнение в прежней области читает готовый план без нового вызова модели. Если подходящего плана ещё нет, чат запрашивает ряд заказов. Цель появляется после согласования. В бэклоге «Обсудить эффект в чате» подставляет выбранную задачу. По её идентификатору AI Core читает сохранённый замер без вызова модели. Ответ показывает статус, окно, сравнение с базой и контрольным рядом при наличии данных, а также следующий шаг. Незавершённый замер отображается как ожидание.

## Серверная история и согласование

Чат хранит приватные сообщения, область и связанные результаты в таблицах `qwen_dialogs` и `qwen_turns` существующей `ai.sqlite3`. Установка обвязки создаёт таблицы только при включении. Долговременный PIM пользуется штатными таблицами и инструментами Core. Личные диалоги остаются в таблицах чата. В общий журнал попадает минимальный отчёт с выбранным предложением и доказательствами после подтверждения. Транзакция сохраняет общий отчёт, согласованную задачу и ключ идемпотентности вместе.

Локальное превью ограничивает чтение диалогов владельцем непрозрачной HttpOnly cookie. В cookie нет текста сообщений. Браузер использует localStorage для координат кнопки. Режим HTTPS берёт владельца из индивидуальной учётной записи Nginx. Доступ к общим данным, срок хранения, очистку истории и резервирование новых таблиц согласуйте с владельцем AI Core. Перенос существующей cookie-истории на персональные аккаунты требует явного сопоставления пользователей.

В черновике редактируются название, описание проблемы, гипотеза, способ проверки и численная цель. Правка способа проверки обновляет соответствующий критерий. Подтверждения, альтернативы, недостающие данные, базовый период, контроль и приоритет берутся из отчёта. Совпадение с бэклогом отображается как предложение пересмотреть существующую задачу. Фактическое сохранение требует явного подтверждения, успешной проверки бэклога и базового уровня. Тег ставит Core. Повтор того же согласования возвращает ту же задачу. Перезапуск продолжает историю при наличии cookie и того же каталога состояния.

## Приёмка HTTPS и командной сборки

`scripts/qwen/rehearse_candidate.py` экспортирует зафиксированные ревизии в пустую внешнюю папку и применяет патчи только там. Понадобятся локальные объекты AI Core `b71424d`, Search `93de546` и Deployment `6c18b37`. Для повторения прежней сборки можно передать `--core f8b93b1 --deployment a57b681`. Скрипт накладывает каталог развёртывания и тесты владельца Deployment, а также модули и тесты владельца Search. Общие настройки и история Git остаются в распоряжении владельца интеграции.

```sh
candidate=$(mktemp -d)
python scripts/qwen/rehearse_candidate.py "$candidate"
cd "$candidate"
PM_EMAIL_ENABLED=false python -m unittest discover -s tests
python scripts/search_release_smoke.py
python scripts/qwen/historical_smoke.py
PM_LLM_URL=http://127.0.0.1:18081/v1 PM_LLM_MODEL=Qwen3-4B python scripts/qwen/historical_smoke.py --live
python scripts/qwen/effect_smoke.py
PM_LLM_URL=http://127.0.0.1:18081/v1 PM_LLM_MODEL=Qwen3-4B python scripts/qwen/effect_smoke.py --live
```

Дополнительный патч `llm_lab/patches/deployment/0001-qwen-proxy.patch` расширяет штатный рендерер Nginx. Рендерер и AI Core используют одни и те же байты объединённого скрипта. Существующий CSP продолжает содержать один SHA-256, а Cookie и Authorization остаются в браузере и на прокси.

Для стенда с HTTPS владелец Deployment настраивает `PM_QWEN_CHAT_ENABLED=true` и `PM_QWEN_OWNER_MODE=proxy` в защищённом `app.env`, а рендерер запускает с флагом `--qwen-chat`. Сгенерируйте случайный служебный ключ через `secrets.token_urlsafe(32)` в защищённом процессе выдачи секретов. Одно значение передайте как `PM_QWEN_PROXY_KEY` в `app.env` и в root-owned файл `/etc/nginx/paradiigma-qwen-proxy.inc` с правами 0600. Файл содержит единственную директиву в следующем формате.

```nginx
proxy_set_header X-Paradiigma-Proxy-Key "<из защищённого хранилища>";
```

Nginx заполняет имя проверенной учётной записью. В Backend подтверждение сверяется в постоянное время. При отсутствии действительного подтверждения маршруты Qwen возвращают 403, в том числе чтение выжимки. Имя должно содержать от 1 до 96 ASCII-символов и начинаться с буквы или цифры. Права на общие расследования и задачи остаются у общей роли Deployment. Режим SSH-туннеля не передаёт имя SSH-пользователя в HTTP. Для отдельных аккаунтов чата нужен HTTPS-маршрут.

Deployment с `4f26aba` содержит поля маркера миграции, защиту пути и `retention-plan`. В сборке с `6c18b37` установите часть `0002-pim-backup-compat.patch` для Core и его регрессионного теста командой `git apply --exclude=scripts/pim_backup.py llm_lab/patches/deployment/0002-pim-backup-compat.patch`. Скрипт репетиции использует этот параметр автоматически. Core отклоняет маркер при непустом WAL даже после свежей копии. Первая репетиция проверила переходы v4 → v5 и v5 → v6. Процедура рабочего перехода с остановкой пишущих процессов описана в руководстве Deployment. [Развёртывание объединённого релиза](https://github.com/GITKITLIT/SoftlineParadiigmaMGR/blob/6c18b37/docs/combined_release_deployment.md)

Проверьте конфигурацию командой `nginx -t`. При обновлении и откате снова соберите конфигурацию из активной ревизии с тем же флагом `--qwen-chat`. Не публикуйте служебный include и вывод полного дампа конфигурации. Тесты требуют Nginx, OpenSSL и htpasswd, создают случайные ключи и сертификат в изолированной папке и работают на loopback. Они проверяют настоящий TLS, отдельные истории двух аккаунтов, хэш CSP и отказ прямому запросу. Для контроля лимитов используйте синтетическую БД.

## Демонстрация R-09

1. Откройте обзор R-09 и компактную выжимку сохранённого исследования. Если отчёта ещё нет, запустите расследование с проверкой релиза, продаж и источников.
2. Откройте кнопку Qwen. Спросите «Почему снизились заказы?». Для воспроизводимого сбора добавьте просьбу сверить воронку, бэклог, интервью и конкурентов.
3. Раскройте шаги расследования, наблюдения и альтернативы. Обратите внимание на автора шага. Выбор Qwen и серверная проверка отмечены отдельно.
4. Спросите «Что проверить первым?» или выберите режим уточнения и спросите про корзину. Сопоставьте фактическое прохождение шага и покрытие регистрации события.
5. Раскройте источники интервью и конкурентов. Уточните дату, признаки сопоставимости и какая информация отсутствует. Живой внешний поиск требует настроенного разрешённого адаптера.
6. Спросите «Как измерить эффект?». Затем откройте черновик исходного ответа, отредактируйте описание проблемы или способ проверки, введите согласованную тестовую цель и подтвердите сохранение. Повторите запрос сохранения с теми же параметрами. В журнале должна быть одна задача с тегом.
7. После обновления страницы снова откройте диалог и серверный бэклог. Действие «Обсудить эффект в чате» запрашивает фактический статус принятой задачи. Отдельно запустите режим симуляции и обозначьте его как синтетический.
8. В базе знаний выберите исторический ряд и два полных окна. Кнопка «Спросить в чате» передаёт выбранную область в новый вопрос. Для демонстрации истории используйте подтверждённые рабочие данные или синтетические наблюдения из [сценариев оценки](../llm_lab/evaluation/scenarios.py).

`scripts/qwen/browser_smoke.py` редактирует тестовую задачу. Запускайте его только с `--isolated-database` и при проверенной изоляции стенда. Флаг `--effect-plan` проверяет раскрытый план и ожидание через интерфейс бэклога. Для БД с сохранённым тестовым замером параметр `--measured-task` принимает название задачи, у которой цель не достигнута и есть контрольный ряд.
