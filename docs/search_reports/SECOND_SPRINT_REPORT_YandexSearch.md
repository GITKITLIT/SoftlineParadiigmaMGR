## Настройка поиска и проверка реального API

1. Создайте или используйте обслуживаемый командой каталог Yandex Cloud с согласованным бюджетом. Нужны роль `search-api.webSearch.user` и ключ с областью `yc.search-api.execute`. Передайте `YANDEX_SEARCH_FOLDER_ID` и `YANDEX_SEARCH_API_KEY` через защищённое окружение процесса. [Официальная инструкция](https://aistudio.yandex.ru/ru/docs/search-api/quickstart/)
2. Задайте `YANDEX_SEARCH_PUBLIC_PRODUCTS` и `YANDEX_SEARCH_ALLOWED_DOMAINS` JSON-массивами разрешённых публичных значений. Необязательный `YANDEX_SEARCH_PUBLIC_ALIASES` задаёт до четырёх проверенных вариантов для канонического имени. Например, синтетическая настройка выглядит как `{"Демо Pro":["Demo Professional","Демо Pro 2026"]}`. Свободный пользовательский вопрос, метрики, интервью и записи бэклога остаются в локальном контуре. Запросы ограничены 400 символами и 40 словами. [Операторы](https://aistudio.yandex.ru/en/docs/search-api/concepts/search-operators) · [Лимиты](https://aistudio.yandex.ru/ru/docs/search-api/concepts/limits)
3. Для одиночной проверки включите `YANDEX_SEARCH_ENABLED=true` и `YANDEX_SEARCH_LIVE_SMOKE=true`. Настройте `PM_PRIVATE_DIR` на разрешённый каталог вне Git. У smoke ровно одна комбинация, одна попытка при доступном бюджете, кеш и прямые страницы отключены.
4. Запустите следующую команду с публичным товаром и конкурентом, разрешёнными для кейса.

```text
python scripts/search_smoke.py --live --product "<публичное имя>" --domain "<домен>" --topic licensing
```

5. Сверьте `status`, `coverage`, `usage.requests`, `attempts[].elapsed_ms` и `attempts[].outcome`. Если провайдер принял запрос, `format`, `response_bytes`, `xml_documents`, `xml_with_passages` и `retained_documents` позволяют проверить реальную структуру и качество извлечения. Оцените вручную совпадение продукта, лицензии и домена по нормализованным свидетельствам. Для повторной проверки других конкурентов согласуйте дополнительные одиночные попытки.
6. Пустая выдача является нормальным `ok` с пустым `items`. Документированный XML-код `15` получает признак `no_results_code`. Реальные отказы доступа, 429 и таймауты фиксируйте при естественном возникновении в согласованном запуске. Для регрессий используйте локальные тесты транспорта. [REST WebSearch](https://aistudio.yandex.ru/ru/docs/search-api/api-ref/WebSearch/search) · [Коды XML](https://aistudio.yandex.ru/ru/docs/search-api/reference/error-codes)

При стандартном бюджете максимум пять сетевых попыток за исследование. По тарифу, проверенному 27.11.2026, номинальная верхняя оценка для пяти попыток составляет 2,440 ₽ днём или 1,830 ₽ ночью с НДС. Ночное окно с 00:00 до 07:59:59 UTC+3. Прогретый кеш без обращений к API даёт 0 ₽ по этому расчёту. `estimate_cost()` использует число попыток и их времена. Это оценка по опубликованному тарифу. Провайдер отдельно оговаривает серверные и авторизационные ошибки, итоговое списание определяется биллингом. HTTP-запросы проверки страниц считаются отдельно. [Тарификация](https://aistudio.yandex.ru/ru/docs/search-api/pricing)

## Допуск к первоисточникам

Прямой обход применяется только к свидетельствам, найденным Yandex Search API, при отдельной настройке и наличии разрешения на обход выбранных сайтов.

| Переменная | По умолчанию | Значение |
| --- | --- | --- |
| `YANDEX_SEARCH_PAGE_FETCH_ENABLED` | `false` | Включение HTTPS-проверки. |
| `YANDEX_SEARCH_PAGE_ALLOWED_DOMAINS` | `[]` | Точный JSON-список, подмножество `YANDEX_SEARCH_ALLOWED_DOMAINS`. |
| `YANDEX_SEARCH_MAX_PAGES_PER_RUN` | `3` | От 1 до 10 уникальных кандидатов. |
| `YANDEX_SEARCH_PAGE_REQUESTS_PER_RUN` | `8` | От 1 до 25 попыток с учётом robots.txt и перенаправлений. |
| `YANDEX_SEARCH_PAGE_DAILY_LIMIT` | `30` | От 1 до 1000 попыток за сутки UTC в общей SQLite. |
| `YANDEX_SEARCH_PAGE_CACHE_TTL` | `3600` | Срок жизни нормализованных фрагментов от 0 до 86 400 секунд. Ноль отключает кеш. |

Защита проверяет HTTPS и стандартный порт, публичность всех адресов DNS-ответа, фактический адрес сокета и TLS-сертификат исходного домена. Каждый переход проходит новую проверку, для другого домена применяется его собственный robots.txt. Политика учитывает правила для робота, шаблоны путей и интервалы запросов. Паузы от `Retry-After` и robots.txt сохраняются в общей БД между запусками. Неясные правила, более длинная пауза, закрытый URL, CAPTCHA, запрещённый тип ответа, скачиваемый файл, превышение 512 КиБ или сбой оставляют сниппет и диагностический код. Запросы выполняются без cookies, Referer и ключа Yandex. HTTP-содержимое обрабатывается статически в памяти. [RFC 9309](https://www.rfc-editor.org/rfc/rfc9309.html)

Поддерживается видимый статический HTML. Динамические приложения, запросы после входа, вложения и разносортные цены без явно связанных условий дают неполные сведения. Доступные URL со служебными параметрами и транзакционные пути исключаются. Попытки очистки текста от типовых инструкций снижают риск, пользовательские тексты и содержимое сайтов в контуре модели остаются недоверенными данными.

## Импорт, AI Core и контракт

1. Подготовьте исследование в отдельной папке вне Git. Если есть предыдущий `PM_EVIDENCE`, добавьте результаты в новый корпус. Оригинал сохраняется. Дедупликация идёт по ID с сохранением исходного порядка. Эталонный лист исключается. Поддерживаются только сохранённые значения формул, а пустые ячейки заполняются исключительно по явным вертикальным объединениям. В матрицах идентичность конкурента берётся из подписей `Конкурент: …` или явно обозначенной группы «Конкуренты».

```text
python scripts/search_import_competitors.py "/local-data/research.xlsx" --corpus "/local-data/existing.json" --output "/local-data/combined.json"
python scripts/search_import_competitors.py "/local-data/research.pptx" --output "/local-data/slides.json"
```

2. После настройки `PM_EVIDENCE` вызывайте сборщик из доверенной конфигурации AI Core. Ленивый импорт и полный пример конверта приведены в [handoff](../search_handoff.md).
3. Передайте отдельно исследовательские записи, проверенный внутренний оффер и результат v1 в функцию сравнения. Опциональный `competitor_aliases` связывает точный домен с именем из внутреннего исследования. Цены требуют одинаковых товара, версии, типа лицензии, срока, количества устройств, НДС, валюты, даты и совместимых данных о подписке. Истечение действия явно опубликованной цены делает её устаревшей.

```python
from pm.yandex_search.comparison import build_comparison_context

context = build_comparison_context(
    web_result=web_v1,
    local_evidence=competitor_records,
    own_evidence=approved_internal_offer,
    competitor_aliases=trusted_display_names,
)
model_evidence = context["qwen_context"]
frontend_matrix = context["matrix"]
source_by_id = context["evidence_index"]
```

4. В агентном цикле присоединяйте `model_evidence` к локальной аналитике, проверяйте возвращённые ID по `model_evidence["evidence"]`, затем формируйте рекомендацию средствами AI Core. `qwen_context` ограничен 24 источниками по умолчанию, 20 сравнениями и байтовым бюджетом отбора. `matrix` содержит 20 строк характеристик и пригодные для таблицы ячейки по конкурентам. Даты для локальных наблюдений выводятся из исследования, для публичной страницы из фактического получения. Сниппету присваивается статус непроверенного наблюдения. Проверенные цены и наличие старше 30 дней и остальные факты старше 120 дней считаются устаревшими. Список гипотез по UX содержит направления дальнейшей проверки и исходные ID.
5. До подключения модели выполните `python scripts/search_investigation_smoke.py`. Сценарий проверяет цепочку от синтетического сигнала и бэклога до конкурентных записей и ссылок в компактном контексте. Для офлайн-симуляций используйте следующий набор состояний.

| Сценарий | Что передать дальше |
| --- | --- |
| Успешный поиск | `status=ok`, нормализованные `items`, `coverage` с количеством кандидатов. |
| Частичная выдача | `status=partial`, пригодные записи и код первой проблемы. `coverage` перечисляет выполненные и пропущенные комбинации. |
| Пустая выдача | `status=ok`, пустой `items`, нулевой счётчик по соответствующей теме. |
| Недоступность | `status=unavailable` и безопасный код вроде `timeout` или `authorization_failed`. Сохраняется локальный контекст. |
| Бюджет исчерпан | `reason=daily_limit` или покрытие `run_limit`. Имеющиеся подходящие записи из кеша доступны. |
| Поиск отключён | `status=disabled`, ноль запросов, возможность продолжить через локальный корпус. |
| Кеш устарел | `warnings` включает `expired_cache`, метрика `expired_cache_entries` растёт. Просроченная запись не используется для актуальной выдачи. |
| Противоречие | `conflict` и ссылки на обе версии. Сниппет с другой цифрой сохраняется как непроверенная альтернатива. |
| Цена не подтверждена | `unverified`, `undated`, `stale` или `incomparable` в сравнении. Разность цен отсутствует. |
| Доказательств мало | `unknown`, отсутствие значения и указание стороны, где нужно исследование. |

В продуктовую аналитику передаётся пригодная для проверки фактура. Поисковая позиция характеризует выдачу. Для доли рынка и бизнес-эффекта требуются независимые данные.

## Снимки, экспорт и запуск по расписанию

В существующей частной папке `--history-dir` создаётся `competitor-history.sqlite3`. История привязана к режиму и публичному плану, использует атомарную блокировку запуска и хранит пригодные снимки для сравнения. Интервал для live по умолчанию 24 часа. Для повторного исследования можно подать обновлённый XLSX/PPTX через импорт и следующий `--offline` снимок. Изменение цены оценивается по умолчанию от 5%, с учётом условий и новой даты. Явное изменение покупки или услуги выделяется с источниками обеих сторон. Исчезновение записи из выдачи отмечается как пробел для проверки.

```text
python scripts/search_monitor.py --demo --history-dir <частная-папка> --report <новый-отчёт.json>
python scripts/search_monitor.py --offline --plan <план.json> --history-dir <частная-папка> --local-corpus <корпус.json> --as-of 2026-11-27 --report <новый-отчёт.md>
python scripts/search_monitor.py --live --plan <план.json> --history-dir <частная-папка> --minimum-interval-minutes 1440
```

План содержит `product`, `domains` и `topics` по контракту v1. Живому мониторингу нужны обычные настройки поиска, отдельный `YANDEX_SEARCH_MONITOR_ENABLED=true` и согласованный бюджет. Для периодического запуска укажите команду `--live` в Windows Task Scheduler или cron с рабочей папкой репозитория и защищённым окружением. Для планового запуска без сети используйте `--offline` со свежим локальным корпусом. CLI делает один проход и завершает процесс. Установка расписания и развёртывание не требуются для офлайн-проверки.

## Фактическая проверка и границы

- Исходный результат первого спринта составлял 44 теста. В итоговом прогоне прошли 77 тестов. Проверены запросы, рейтинг, лимиты и срок кеша, XLSX и PPTX, история, конфликты, первоисточники и сетевой транспорт на loopback. Предупреждение `ResourceWarning` в старом тесте Метрики воспроизводилось на исходной ревизии.
- `python scripts/search_investigation_smoke.py` прошёл. Синтетика вернула пять пригодных для поиска ID, два ID для Qwen, три компактных сравнения и 20 строк матрицы. Вызов Qwen в этой проверке не нужен.
- `node --check web/app.js` прошёл. Браузерный регрессионный сценарий завершился с `UI PASS`. Совместное расследование с AI Core и локальной моделью проверяется после объединения веток.
- За 48 офлайн-циклов на `28434cb` медиана новой SQLite составила 41,05 мс, при попадании в кеш 5,95 мс. В 48 параллельных вызовах с 12 потоками и одной БД получено одно обращение к имитатору, 47 попаданий в кеш и p95 195,9 мс. Весь параллельный прогон занял 309,8 мс. Это замер адаптера и локального хранения.
- Ключи и согласованный бюджет для платного запроса в сессии отсутствовали. Фактическое число запросов к Yandex Search API и сайтам конкурентов за проверку — 0. Фактическая облачная задержка, счёт и соответствие выдачи продуктам Softline пока неизвестны. Проверка HTTP на loopback и эмуляция ответов явно отделены от live.
- Разрешённые локальные пути к исследованиям Softline отсутствовали. Импорт проверен на синтетических XLSX и PPTX, включая объединения, разные листы, формулы без сохранённого результата, сравнительные матрицы, таблицы внутри слайдов и сохранение интервью.
- Между отдельными процессами общий бюджет атомарен. Один холодный запрос может быть отправлен несколькими процессами при разных вызовах, а внутрипроцессный кеш объединяет их. Частота обхода страниц на домен резервируется в общей SQLite. Поисковая квота в несколько процессов дополнительно контролируется самим провайдером.
