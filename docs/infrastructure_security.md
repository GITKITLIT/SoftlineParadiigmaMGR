# Доступ команды и демонстрации

Backend слушает IPv4 loopback на порту 8080. SQLite обслуживается внутри процесса. Индивидуальные SSH-ключи или пароли Nginx дают доступ к одной базе команды. Серверный бэклог общий, а черновики панели «Демо-бэклог» хранятся в localStorage каждого браузера. Рабочий сервер предназначен для доверенных пользователей одного контура с одинаковым правом читать исследования, принимать задачи и видеть отчёты.

## Development через SSH

1. Капитан разрешает в группе безопасности вход TCP/22 только с согласованных адресов или VPN. Каждый из пяти участников создаёт собственный Ed25519-ключ с парольной фразой. Например, Тимур выполняет `ssh-keygen -t ed25519 -a 64 -f ~/.ssh/paradiigma-team -C timur`. Капитану передаётся только файл `.pub` по согласованному каналу. Отпечатки пользовательских ключей и ключа хоста сверяются независимо.
2. На Ubuntu администратор создаёт группу `pm-tunnel` и персональные логины, например `pm-timur`, `pm-artur`, `pm-amir`, `pm-andrey`, `pm-max`. Используйте эти пять логинов отдельно от сервисных учётных записей и от административного логина `paradiigma`. Для каждого аккаунта укажите `--shell /usr/sbin/nologin`, разрешите только вход по ключу. На чистой Ubuntu с PAM команды для первого участника выглядят так:

   ```sh
   sudo groupadd --system -f pm-tunnel
   sudo adduser --disabled-password --gecos '' --shell /usr/sbin/nologin pm-timur
   sudo usermod -aG pm-tunnel pm-timur
   sudo install -d -o root -g root -m 0755 /etc/ssh/pm-authorized-keys
   sudo install -o root -g root -m 0644 timur.pub /etc/ssh/pm-authorized-keys/pm-timur
   ```

3. Добавьте `Include /etc/ssh/paradiigma-tunnel.conf` **последней строкой** основного `/etc/ssh/sshd_config`. Исходный файл с блоком `Match Group` — `deploy/ssh/tunnel-users.conf`, владелец копии в `/etc/ssh` — root, права 0644. Перед reload оставьте открытой административную сессию. Проверьте `sudo sshd -t` и эффективные настройки для участника и администратора, например `sudo sshd -T -C user=pm-timur,host=localhost,addr=127.0.0.1`. Для участника ожидаются `maxsessions 0`, `allowtcpforwarding local`, `permitopen 127.0.0.1:8080`, `allowstreamlocalforwarding no` и `authenticationmethods publickey`. Затем выполните `sudo systemctl reload ssh` и проверьте новую сессию администратора. [Параметры OpenSSH](https://man.openbsd.org/sshd_config)
4. Каждый участник использует свой логин, ключ и проверенное имя сервера. На Linux/macOS и Windows с OpenSSH Client команда имеет одинаковый вид:

   ```sh
   ssh -NT -o IdentitiesOnly=yes -o ExitOnForwardFailure=yes -o ServerAliveInterval=30 -i ~/.ssh/paradiigma-team -L 127.0.0.1:18080:127.0.0.1:8080 pm-timur@team.example.org
   ```

   Откройте `http://127.0.0.1:18080/`. Браузер отправит Host и Origin локального туннеля. Сервер разрешает имя `127.0.0.1` и проверяет полное совпадение локального Origin с Host, включая порт. Локальный слушатель доступен другим процессам на рабочей станции. Используйте доверенные станции.
5. Для отзыва удалите соответствующую строку из root-owned файла ключей и завершите существующие соединения данного SSH-пользователя, включая туннели. После отзыва проверьте новый вход и недоступность старого туннеля. Доступ к HTTPS отзывается отдельно.

## HTTPS на выделенном узле

Нужны утверждённый DNS-адрес, действительный серверный сертификат с полной цепочкой, соответствующий закрытый ключ и право открыть HTTPS для выбранной аудитории. Без них используется SSH. В группе безопасности и локальном firewall разрешите TCP/443 со стороны аудитории, TCP/22 с административных адресов. Порты 8080, порт модели и HTTP/80 закрыты для внешних адресов, включая IPv6. Если сертификат выдаётся через ACME, DNS-01 позволяет оставить порт 80 закрытым. Согласуйте выдачу и продление с владельцем домена.

На Ubuntu 24.04 установите `nginx apache2-utils`. Команды ниже выполняет администратор после настройки внешнего firewall. Удалите из sites-enabled ссылку на заводской сайт Ubuntu при её наличии на **выделенном** узле. Проверьте все активные `listen` с помощью `nginx -T` в закрытой администраторской сессии. Шаблон включает HTTPS-сервер по умолчанию, отклоняющий чужое TLS-имя. На хосте с другими сайтами капитан должен согласовать единственный default_server. [Обработка TLS в Nginx](https://nginx.org/en/docs/http/ngx_http_ssl_module.html#ssl_reject_handshake)

Укажите DNS-имя и режим. Шаблон ожидает цепочку и ключ в `/etc/letsencrypt/live/<имя>/`. При корпоративном сертификате администратор меняет две директивы `ssl_certificate*` в сгенерированном файле. Закрытый ключ читает root. Метку `demo` используйте только на отдельной демонстрационной машине по процедуре ниже.

```sh
cd /opt/paradiigma/current
domain=pm.example.org
python3 scripts/deploy/render_proxy.py "$domain" --mode production > /tmp/paradiigma-site.conf
sudo install -o root -g root -m 0644 /tmp/paradiigma-site.conf /etc/nginx/sites-available/paradiigma
sudo ln -sfn /etc/nginx/sites-available/paradiigma /etc/nginx/sites-enabled/paradiigma
sudo touch /etc/nginx/paradiigma.htpasswd
sudo chown root:www-data /etc/nginx/paradiigma.htpasswd
sudo chmod 0640 /etc/nginx/paradiigma.htpasswd
sudo htpasswd -B /etc/nginx/paradiigma.htpasswd pm-timur
sudo nginx -t
sudo systemctl enable --now nginx
sudo systemctl reload nginx
```

Повторите `htpasswd -B` с персональным именем для каждого допущенного участника. Пароль вводится в интерактивном приглашении. Флаг `-D` удаляет запись при отзыве. Выделите отдельные аккаунты жюри со сроком ручного отзыва. Страница и все проксируемые маршруты требуют Basic Auth поверх TLS. Имя пользователя не передаётся Backend. У приложения пока нет индивидуальных ролей и аудита авторства решений.

Nginx проверяет внешний Host и Origin до изменения заголовков. POST разрешён только с точным `https://<имя>`. GET поддерживает навигацию без Origin. Затем запрос получает фиксированные `Host: 127.0.0.1:8080` и `Origin: http://127.0.0.1:8080`. Nginx передаёт тип содержимого и служебные поля транспорта, отбрасывая клиентские Authorization, Cookie и Forwarded. Локальные проверки в `app.Handler` продолжают работать. HTTP API принимает JSON до 150000 байт. Граница удерживает 12 одновременных запросов на IP, 32 на сайт и 6 запросов/с на IP с коротким всплеском до 24. Они могут суммироваться для коллег за одним NAT. Изменяйте `limit_*` и `proxy_read_timeout` (по умолчанию 300 с между чтениями) по замерам Амира, затем проверяйте `nginx -t`. Прокси-таймаут не отменяет уже начатое расследование в Python. [Параметры проксирования Nginx](https://nginx.org/en/docs/http/ngx_http_proxy_module.html)

Шаблон вычисляет CSP-хеш встроенного JavaScript из `web/app.js` конкретного релиза. **При каждом обновлении или откате с HTTPS** повторно сгенерируйте конфигурацию из активного `/opt/paradiigma/current`, сохраните режим площадки, перенесите локальные пути сертификатов и настройки лимитов, проверьте `nginx -t` и выполните reload. Проверьте загрузку страницы и POST из браузера. Аналогично настройте reload после успешного продления сертификата. Разрешено только обращение браузера к API того же origin. HSTS действует год на имени площадки.

Журнал доступа содержит время, метод, статус и длительность. Путь, параметры, учётные данные и тело запроса в формат не входят. Ошибки Nginx записываются с уровня crit. Проверьте владельцев, режимы 0640 или строже и ротацию этих двух файлов через `/etc/logrotate.d/nginx`. Для диагностики не включайте debug-лог и не выгружайте полный системный журнал за пределы контура.

### Синтетическая демонстрация

1. Подготовьте **отдельную чистую VM** с собственным доменом, новым диском, системными пользователями, ключами и каталогом копий. Группы безопасности разделяют рабочую сеть и демо. К VM не подключают рабочие документы, диски, резервные копии, персональные токены или SSH-агент. У неё нет сервисной учётной записи с доступом к рабочим ресурсам. Установите одобренный коммит по инструкции развёртывания.
2. Сохраните шаблон `deploy/app.env.example` с `PARADIIGMA_MODE=demo`, пустыми путями данных/импорта, выключенным поиском, сборщиком и пустыми токенами. `PM_PRIVATE_DIR` указывает на отдельный каталог VM. Установите `deploy/demo/loopback-only.conf` в `/etc/systemd/system/paradiigma.service.d/loopback-only.conf` (директория root:root 0755, файл root:root 0644), затем выполните `systemctl daemon-reload` и `systemctl restart paradiigma`. Правила cgroup BPF должны действовать на ядре Ubuntu. Примените также внешний запрет исходящего трафика VM к рабочей сети и публичным API. При необходимости Qwen разверните локально с демо-моделью и loopback endpoint.
3. Создайте HTTPS-сайт на этой VM с `--mode demo`, где маршрут загрузки текстовых материалов закрыт. Для показа берите только синтетические запросы и записи. Свободные текстовые поля в расследованиях сохраняются. Показывайте общий серверный бэклог через учётную запись демо, в отдельном профиле браузера, чтобы изолировать черновики localStorage. После показа отзовите учётные записи, сохраните или удалите синтетические данные по решению капитана.
4. Приёмка с клиентской машины: проверить сертификат без пропуска проверки TLS, 401 до входа, открытие UI после входа, загрузку данных настроек без живых интеграций и отказ импорта. Проверить ожидаемые слушатели командой `ss -lntp` на VM, совпадение сертификата с DNS-именем и закрытие портов 8080/модели из клиентской сети. Рабочий контур и демонстрационный обслуживают свои каталоги данных и копии даже при одинаковых абсолютных путях.

## Аудит данных, ответы и изменения для AI Core

* `app.page` включает evidence, обзор и настроенный benchmark в HTML. `/api/search`, `/api/analysis/report`, память и Redmine export возвращают рабочие сведения авторизованным участникам. `ai_store.public_report` отдаёт статусы и ограниченные агрегаты. Утверждать публикацию должен владелец данных. Файлы `build/index.html`, отчёты, XLSX и содержимое браузерного хранилища требуют тех же прав, что исходные материалы.
* В текущем AI Core OAuth передаётся в заголовке запроса Метрики, а `/api/analysis/settings` сообщает признаки настройки и разрешённые публичные значения. Тесты отправляют случайный тестовый маркер через конфигурацию и проверяют HTTP, отчёт и диагностику. Это покрывает проверенные маршруты. Свободный текст, включая приватные сведения в названиях или введённом фрагменте, может вернуться в исследовании. Для Тимура: вынести разрешённые поля публичного вывода в общий контракт и добавить регрессионные проверки на каждый новый экспорт, источник и формат ошибки.
* Backend передаёт пользователю первые 200 символов некоторых `ValueError`. Парсеры и прикладной код иногда включают входные значения в сообщение. Для Тимура: хранить стабильные коды ошибок и возвращать заранее определённые тексты по коду. Клиентскому журналу не нужны содержимое запроса, секреты или traceback. Ошибка GET до формирования ответа должна возвращать контролируемую ошибку сервиса.
* Код `scripts/ai_export.py` создаёт файл с режимом, зависящим от umask оператора. Для частных экспортов используйте каталог 0700 вне checkout и `umask 077` в сессии. Для Тимура: явно создавать закрытые экспорты с 0600 и проверять права в тесте. Датасеты, базы, ключи, архивы и отчёты перед push проверяются сканером Git index. Произвольные токены и смысловую конфиденциальность текста проверяет владелец.
* Для внедрения с разными полномочиями определить внутри Backend роли чтения, импорта и принятия задач, привязать действие к доверенной идентичности и добавить журнал решений без тела запроса. До этого отдельный экземпляр требуется для каждой группы с собственным набором разрешённых данных. Посторонний процесс с доступом к loopback может использовать локальный API, поэтому административный shell предоставляется только доверенным операторам.

Воспроизводимая синтетическая проверка Nginx (реальные TLS, Basic Auth, временный Backend и виртуальный домен): `python -m unittest discover -s tests -p test_deployment_proxy.py -v`. Для полного теста нужны Nginx, OpenSSL и htpasswd. Запуск использует свободные loopback-порты и временные ключи, каталог удаляется после завершения.
