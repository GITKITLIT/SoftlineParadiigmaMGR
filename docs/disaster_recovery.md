# Независимые резервные копии и восстановление

## Что окажется в снимке

Единица восстановления содержит `ai.sqlite3`, манифест с временем UTC, версией схемы и SHA-256 каждого файла, а также прежний `PM_PRIVATE_DIR/sources.json`, если он имеется. Расследования, решения, очередь, импортированные выдержки и продуктовая память хранятся в SQLite. Служба вызывает `scripts/pim_backup.py` команды AI Core. Соединение открывается для чтения, SQLite Online Backup API читает согласованный снимок, включая зафиксированные транзакции WAL. При наличии старого `sources.json` храните его как статический файл или заменяйте атомарным переименованием.

Для восстановления всего рабочего места капитан ведёт отдельную опись источников. Храните выпущенные версии оригинальных документов, файлов `PM_WORKBOOK`, `PM_SNAPSHOT`, `PM_EVIDENCE`, `PM_CASE_CONFIG` в одобренном закрытом хранилище. В опись заносите версию объекта, контрольную сумму, дату, совместимый SHA приложения и идентификатор набора данных. Закрытую конфигурацию и ключи восстанавливает администратор из согласованного менеджера секретов. Веса и исполняемый файл Qwen восстанавливают из проверенного дистрибутива с утверждёнными хешами. Для новых отдельных БД после интеграции поискового адаптера Тимур и Артур определяют, какие данные требуют отдельного снимка и какие кеши допустимо перестроить. До приёмки требуется реальная опись всех настроенных входов.

## Права, расписание и контроль

Установщик вызывает `scripts/deploy/install-backup.sh`. Сервис `pm-backup` имеет дополнительную группу `pm-db` только при запуске через systemd. Каталог базы с родительской группой `pm-db` и битом setgid даёт чтение рабочей SQLite и журналов. Для ранее перенесённых файлов администратор проверяет группу и чтение (`0640` для базы и статического `sources.json`). Служба получает только читаемое представление каталога через `run-paradiigma_backup_input.mount`. Перед копированием она проверяет флаги `ro,nosymfollow` в своём namespace. На неподходящем ядре или при отсутствии флагов запуск завершается ошибкой. Служба работает без сети, доступа к домашним каталогам, конфигурации приложения и каталогам документов.

| Путь | Владелец и режим | Назначение |
|---|---|---|
| `/var/lib/paradiigma/db` | `pm-app:pm-db 2750` | Рабочая SQLite и её журналы |
| `/var/backups/paradiigma` | `pm-backup:pm-backup 0700` | Локальный независимый том или каталог |
| `/var/lib/paradiigma-backup-status` | `pm-backup:pm-app 2750` | Публикация `status.json` с режимом `0640` |

Таймер запускает службу ежедневно в 02:00 UTC со случайной задержкой до 15 минут и догоняет пропущенный запуск после перезагрузки. Служба последовательно создаёт временную копию, проверяет внешние ключи и `integrity_check`, восстанавливает её в пустой рабочий каталог и проверяет SHA-256. Затем она синхронизирует файлы и каталог, публикует снимок под уникальным именем и удаляет снимки старше 14 дней. Неудачный тест восстановления оставляет прежние снимки доступными. Локальные права защищают копии от приложения и Qwen. Владелец резервного сервиса обладает правом удаления для ротации. Общий диск с VPS сохраняет риск утраты обоих наборов при аварии узла.

Планируйте место как сумму действующих снимков и двух полных временных экземпляров на создание и пробное восстановление. Частые предрелизные снимки тоже занимают место. Сравнивайте допустимую потерю данных с фактическим возрастом последнего успешного снимка. При исправном ежедневном расписании номинальный интервал до 24 ч 15 мин плюс время копирования. Целевой RPO и полный RTO утверждает капитан. `restore_seconds` измеряет только пробное восстановление данных.

После создания первой продуктовой базы и перед обновлением выполните:

```bash
sudo systemctl start paradiigma-backup.service
systemctl list-timers paradiigma-backup.timer
sudo journalctl -u paradiigma-backup.service -n 20 --no-pager
sudo -u pm-app cat /var/lib/paradiigma-backup-status/status.json
```

Статус содержит результат, времена последнего бэкапа, проверки целостности, пробного восстановления, длительность и время последнего сбоя при наличии. После сбоя прежние успешные времена сохраняются. Если systemd не смог запустить процесс (например, ошибка mount unit), JSON может остаться старым. Для приёмки проверяйте и код завершения службы, и возраст JSON. Публичного HTTP-метода восстановления нет. Локальную диагностику читает оператор или `scripts/deploy/health.py`.

Для изменения срока используйте `sudo systemctl edit paradiigma-backup.service` и задайте `Environment=PARADIIGMA_RETENTION_DAYS=30` в секции `[Service]`. Изменение частоты делается drop-in таймера с обнулением старого `OnCalendar=`. При терабайтной базе измерьте время. AI Core ограничивает саму операцию SQLite Backup API 100 секундами, предел запуска службы равен 10 минутам. Настройку окна и лимитов согласуйте с Тимуром на синтетическом объёме данных.

## Восстановление администратором

Выполняйте переключение в закрытое окно обслуживания после подтверждения выбранного времени данных. Остановите входящие HTTP-запросы и все отдельные процессы, способные писать в рабочую базу, включая CLI импорта. Определите совместимый SHA приложения по журналу релизов. Сохраните старую БД и её sidecar-файлы вместе в отдельном каталоге. При потере диска сначала поднимите чистый хост с теми же пользователями и версиями, верните конфигурацию и оригиналы документов из описи.

Для штатной установки на одном разделе передайте скрипту точное имя выбранного снимка. Выберите снимок с ожидаемыми временем и схемой. Для удалённой копии сначала скачайте согласованные версии объектов на закрытом узле, проверьте происхождение и поместите выбранный каталог под `/var/backups/paradiigma` с доступом только `pm-backup`.

```bash
cd /opt/paradiigma/current
read -r -p 'Имя снимка (pim-…): ' snapshot
sudo bash scripts/deploy/restore.sh "$snapshot"
```

Скрипт разделяет блокировку с установщиком, временно выключает расписание, вызывает проверку и восстановление с правами pm-backup. Он проверяет схему по метке активного релиза, останавливает Backend и mount unit, переключает каталог и ждёт ответа HTTP. При неудачном запуске возвращает предыдущий каталог. Новый снимок и статус подтверждают резервирование восстановленного набора. Закрытая папка recovery.* содержит прежнюю базу, промежуточные файлы и при ошибке переключения неудачный набор. Сохраните её на согласованный срок. При повреждении снимка сохраните его для разбора и повторите проверку с предыдущим локальным снимком или конкретной версией объекта. До открытия доступа проверьте прежнее расследование, состояние задачи, даты восстановленных сведений, внешние источники и фактические RPO/RTO.

Для тома, смонтированного прямо на db, подготовьте новый том на закрытом узле. Проверьте снимок через `pim_backup.py verify --snapshot PATH`, вызовите `restore-test --snapshot PATH --output NEW_DIR` и проверьте схему и разрешения на новом томе. При остановленных Backend, таймере, backup service и mount unit отмонтируйте прежний том, смонтируйте новый в 2750 pm-app:pm-db и проверьте права 0640 pm-app:pm-db на данных. Обновите проверенную конфигурацию монтирования на перезагрузку. Запустите Backend, backup service и таймер и проверьте доступность и данные до открытия записи. При неуспехе до открытия записи остановите службы и верните прежний том. После возобновления записи возврат требует отдельно согласованного переноса новых решений.

## Второй экземпляр в Yandex Object Storage

Капитан согласует размещение данных, стоимость и область доступа до подключения. В отдельном облачном контуре создают закрытый бакет, включают версионирование и заранее согласованное шифрование. Если утверждена неизменяемость, включают Object Lock и задают срок блокировки новых версий **до** первой загрузки. Режим strict compliance и длительность требуют отдельного решения из-за ограничений на досрочное удаление и оплаты места. [Версионирование](https://yandex.cloud/ru/docs/storage/concepts/versioning) · [Блокировка версий](https://yandex.cloud/ru/docs/storage/concepts/object-lock)

Выгрузку выполняет отдельный процесс на допущенном узле с выделенной идентичностью. Администратор передаёт ему только уже проверенный каталог снимка в отдельной закрытой очереди выгрузки. Credеntials загрузчика ограничивают записью в выделенный префикс, без изменения политики, версионирования, блокировок и удаления версий. Приложение, Qwen и служба локального копирования этих credentials не получают. Для восстановления выделяется другая идентичность с чтением нужных версий. Назначайте права и на уровне IAM, и на уровне бакета с проверкой итоговых разрешений. [Политика доступа](https://yandex.cloud/ru/docs/storage/security/policy)

Загрузчик кладёт файлы под уникальным префиксом идентификатора снимка, затем манифест. В закрытом каталоге восстановления записывает ключ, возвращённый version ID каждого объекта и SHA-256 манифеста. Прерванную выгрузку без полного набора версий считают незавершённой. На независимом узле администратор скачивает именно зарегистрированные версии, проверяет хеш манифеста и выполняет `verify` и `restore-test`. Учитывайте хранение всех версий, репликацию конфигурации и доступность ключа шифрования при потере исходного VPS. Проверка локальной копии и её JSON-статус охватывают только локальный том. Внешнюю выгрузку, аудит прав загрузчика и контрольную загрузку из бакета капитан принимает отдельно.

## Повторяемая проверка

На синтетической базе `python3 -m unittest discover -s tests -p test_deployment_backup.py -v` проверяет снимок при активной WAL-транзакции, legacy-документ, отбрасывание повреждённой копии, безопасную ротацию и отклонение символьных ссылок. Тот же тест под root в одноразовой Linux VM запускает процессы с разными непривилегированными UID и проверяет запрет чтения, изменения, переименования и удаления копий пользователем приложения, а также чтение и запрет перезаписи статуса. Тесты создают данные в системном временном каталоге. При приёмке чистой Ubuntu отдельно запустите реальный unit на синтетических данных и проверьте права создаваемой базы, флаги mount, JSON, автозапуск таймера и переоткрытие после перезагрузки.
