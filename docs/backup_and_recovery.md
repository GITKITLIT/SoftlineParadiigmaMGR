# Резервное копирование и восстановление

CLI scripts/pim_backup.py отделён от веб-инструментов и процесса модели. Он открывает рабочую SQLite read-only, создаёт копию через SQLite Backup API, проверяет integrity_check и foreign_key_check и пишет манифест SHA-256. Имя каждого каталога уникально. Сервер получает только статусный JSON. Проверенная синтетическая репетиция не подтверждает системные права или шифрование конкретного VPS.

## Подготовка Linux

Единая раскладка использует пользователей pm-app, pm-qwen и pm-backup. База находится в /var/lib/paradiigma/db, независимые копии в /var/backups/paradiigma. Служба резервирования читает представление рабочей БД через mount с ro,nosymfollow. Отдельный читатель SQLite удерживает WAL во время копирования. Backend читает только status.json. Подготовьте роли, mount и systemd по [руководству аварийного восстановления](disaster_recovery.md).

После установки запустите от root команду sh deploy/check_backup_isolation.sh для проверки базовых эффективных прав. Выполните сценарий Ubuntu из CI для проверки реального mount, чтения активного WAL, восстановления и ограничений AppArmor. Серверный переход v5 → v6 проводят со свежей копией остановленной БД и проверкой отсутствия непустого WAL. [Порядок развёртывания](combined_release_deployment.md)

## Проверка копии и восстановления

- Создание от backup-пользователя: python scripts/pim_backup.py create --db DATABASE --directory INDEPENDENT_TREE --status-file SAFE_STATUS. Опциональные документы передавайте только утверждёнными явными --document PATH. Снимок SQLite уже включает извлечённые тексты, версии и FTS-индекс.
- Проверка: python scripts/pim_backup.py verify --snapshot SNAPSHOT_DIR.
- Восстановление: python scripts/pim_backup.py restore-test --snapshot SNAPSHOT_DIR --output NEW_PRIVATE_DIRECTORY. Каталог должен быть новым. Команда не заменяет рабочую БД. Укажите отдельный PM_PRIVATE_DIR и порт, запустите приложение и повторите историческое сравнение, поиск исследования, проверку связей и тестовую запись.
- Перед миграцией остановите пишущие процессы. Создайте независимую копию и проверьте восстановление. Затем запустите новую версию с PM_MIGRATION_STATUS_FILE. При неудаче сохраняйте состояние для анализа. Возвращайте прежний код на отдельной директории из снимка и переводите пользователей только после проверки. Приложение не умеет выполнять административную замену рабочей БД.
- При повреждении архива исключите его через verify и выберите предыдущий проверенный снимок. Сверяйте целостность и версию при каждом восстановлении.

Команда python scripts/pim_backup.py retention-plan --directory TREE только показывает распределение 48 часов, 30 дней, 12 недель и приблизительно 12 месяцев и кандидатов на ротацию. Она всегда оставляет последнюю копию. Проверьте защищённые копии перед миграциями и требования компании. Срок хранения продуктовой истории не связан с ротацией. Удаление выполняет отдельный администратор по подтверждённому правилу.

## Независимая зашифрованная копия

Храните рабочий экземпляр, локальную копию на независимом зашифрованном томе и третью копию вне сервера. CLI пишет обычный SQLite-файл в переданный каталог, поэтому шифрование диска или архивирование с утверждённым ключом требуется до передачи. В Object Storage используйте отдельное приватное хранилище, шифрование KMS, версионирование и Object Lock при согласованной политике. Загружайте только уже проверенные снимки по TLS под отдельной служебной учётной записью без доступа у backend и модели. Права удаления и управления сроками держите отдельно от uploader. Проверяйте восстановление из object version, а также политику неизменяемости. [Версионирование](https://yandex.cloud/en/docs/storage/concepts/versioning) · [Object Lock](https://yandex.cloud/en/docs/storage/concepts/object-lock) · [Шифрование](https://yandex.cloud/en/docs/storage/concepts/encryption)

Плановые цели требуют утверждения владельцем. Штатный таймер запускает ежедневный снимок в 02:00 UTC с задержкой до 15 минут. Для меньшего RPO пересчитайте расписание после замеров на целевом объёме и проверке восстановления. Повреждение или ошибка таймера повышает фактический RPO, за ним нужен мониторинг. Цель RTO определяется по репетиции на объёме рабочей БД и включая выгрузку внешнего архива. Замер на синтетических данных приведён в отчёте и не заменяет замер VPS.
