# Эксплуатация и приёмка

## Ежедневная проверка

На сервере приложение, модель и резервное копирование используют разные учётные записи. Диагностику запускают с правами чтения приложения. После первого успешного резервирования выполните:

```sh
cd /opt/paradiigma/current
sudo -u pm-app python3 scripts/deploy/health.py
systemctl list-timers 'paradiigma*'
systemctl show paradiigma.service -p ActiveState -p NRestarts -p MemoryCurrent -p CPUUsageNSec
journalctl -u paradiigma.service --since today -p warning --no-pager
```

Добавьте `--expect-qwen`, когда приёмка требует работающую модель. Скрипт обращается только к портам loopback, проверяет JSON и задержку HTTP, собирает загрузку CPU за короткий интервал, занятую и общую RAM из /proc, свободное место, размер файла SQLite и WAL. Он читает агрегаты синхронизации продаж и Метрики и число расследований с ошибками/частичными результатами Метрики и поиска среди последних 20. Для Метрики и поиска отдельно указывается время последнего успешного расследования с таким источником. Время последнего успеха синхронизации может отсутствовать при отключённом сборе. Счётчик failed_jobs отражает текущее состояние записей заданий, а не общее число неудачных попыток за всё время.

Нулевой код означает, что Backend ответил, рабочая схема доступна, метки создания, проверки целостности и пробного восстановления свежие и требуемый модельный endpoint ответил. Порог свежести по умолчанию 36 часов. Настройте его согласованно с таймером и согласованным RPO. Ненулевой код при первой установке ожидаем до создания и восстановления первой копии. При сбое проверьте service/timer, свободное место на **обоих** томах, дату UTC и права каталогов. При сбое источника посмотрите только его код состояния в журнале расследований, проверьте срок действия доступа и бюджет через уполномоченного владельца. Повторный live-запрос может тарифицироваться.

CPU процесса за период удобно измерить по разности CPUUsageNSec двух вызовов systemctl show, поделённой на длину интервала в наносекундах. Host CPU включает соседние службы. Следите за запасом диска с учётом следующего полного снимка, проверки восстановления и WAL. Отслеживайте тренд, подбирайте пороги по измерениям на целевой машине.

Логи служб собирает journald. Ограничьте доступ к группам adm/systemd-journal. Для просмотра используйте фильтрацию по unit и времени. Для выделенного узла администратор определяет общий бюджет журнала в /etc/systemd/journald.conf.d/ по свободному месту (`SystemMaxUse`, `MaxRetentionSec`) и проверяет `journalctl --disk-usage`. Эти параметры затрагивают весь сервер. Текст запроса, содержимое EnvironmentFile, исходные документы, полный HTML и исследования нельзя прикладывать к заявке об инциденте. Для тикета достаточно времени UTC, SHA, unit, кода состояния и числовых показателей.

## Расчёт стоимости

Капитан заполняет входные данные по региону, валюте RUB, налоговому режиму и дате своего предложения. Скрипт принимает эффективную цену за единицу после скидок и бесплатных объёмов. Пересчитайте ступенчатые цены и налоги в эффективную ставку перед вводом. [Калькулятор Yandex Cloud](https://yandex.cloud/ru/prices)

```sh
umask 077
python3 scripts/deploy/estimate_cost.py --template > "$HOME/pm-cost.json"
# Введите параметры и цены из предложения в закрытый файл.
python3 scripts/deploy/estimate_cost.py --input "$HOME/pm-cost.json"
```

| Статья | Как получить месячный объём |
|---|---|
| VM приложения | Часы работы × цена всей выбранной конфигурации vCPU и RAM в час |
| Вычисления Qwen | При совместном размещении уже входят в VM. Для отдельного узла учитываются его фактические часы и полная цена конфигурации, включая GPU при наличии |
| Диски | GB-месяцы системного тома, данных, весов и локальных копий. Для разных типов дисков разделите общую стоимость на суммарный объём |
| Объектные копии | Средний объём **всех версий**, включая заблокированные и временно перекрывающиеся версии, умноженный на цену GB-месяца. Для полного ежедневного снимка оцените размер × число хранимых снимков |
| Операции хранения | Тысячи тарифицируемых PUT/GET и операций восстановления. Для разных видов операций введите средневзвешенную цену |
| Сеть | Часы публичного IPv4 и тарифицируемые GB исходящего трафика после льгот, включая перенос между узлами и скачивание копий |
| Внешние источники | Тысячи оплачиваемых запросов Search API по фактическому расходу после кеширования и суточных лимитов |

Каждая строка равна объёму × ставке. Сумма строк даёт месячный бюджет, деление на число менеджеров даёт распределённую стоимость места. Для сценариев с 1 и 5 менеджерами измените также объём запросов, трафик и часы узла по ожидаемой нагрузке. Сервер и диски учитываются один раз на инсталляцию. Сравните совместное и раздельное размещение на одном наборе запросов. Валидатор требует явного нуля для неиспользуемого ресурса.

Амир и капитан фиксируют процессор, RAM, модель/квантование, число слотов llama.cpp и число одновременных пользователей. На синтетическом контуре с одобренными весами запустите `python scripts/ai_smoke.py --mode real --runs 10` и запишите median/p95, статусы, успешные ответы и расход токенов. Серийный smoke не измеряет конкуренцию. Отдельно повторите одновременные расследования и посчитайте ответы с fallback/busy. Сравните спрос в пиковый час с числом **успешных модельных** ответов в час до покупки ресурсов. Тариф, ёмкость VPS и результат этого замера должен предоставить владелец. Расход на администрирование и сроки восстановления оцениваются отдельно.

## Проверка перед публикацией

После добавления файлов в индекс и до отправки выполните:

```sh
python3 scripts/deploy/scan_index.py --since origin/feature/deployment
```

При первом создании ветки укажите доверенную базовую ревизию. Проверка видит staged-файлы и историю публикуемых коммитов, включая секрет, удалённый более поздним коммитом. Она выводит тип совпадения без значения. Проверьте содержимое всех новых файлов и синтетических источников перед отправкой, поскольку сканер распознаёт заданные форматы, а происхождение данных проверяет человек.

## Возможная миграция на PostgreSQL

Решение принимает капитан по замерам ожидания записи, объёма и требуемого числа экземпляров. Вначале Тимур выделяет слой доступа к данным и переносит транзакции, INSERT ON CONFLICT, JSON-запросы, первичные и внешние ключи, версию схемы, полнотекстовый поиск и выдачу заданий с lease. Добавляет интеграционные проверки параллельных решений и идемпотентности. Администратор готовит закрытую сеть, отдельные роли владельца схемы, приложения и резервного копирования, TLS с проверкой узла и пробный pg_dump/pg_restore.

На синтетической копии, затем на согласованной закрытой репетиции загрузите таблицы в порядке зависимостей, сохраните идентификаторы расследований, задачи, версии наблюдений, связи доказательств, даты UTC и значения последовательностей. Сравните количество строк, нарушения ссылок, контрольные агрегаты и выборку историй до/после, затем повторите поиск, отчёт и принятие решения. Перед переключением остановите записи и сборщики, снимите и проверьте финальную SQLite-копию, повторите перенос и smoke до открытия доступа. Сохраните доступный только администратору исходный набор. Возврат до открытия записи использует исходный SHA и SQLite. При появлении новых записей сначала требуется сверка и перенос дельты. Срок отката, RPO и RTO утверждаются на репетиции.
